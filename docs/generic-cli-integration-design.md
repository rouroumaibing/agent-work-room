# 通用 Agent 对接外部 CLI 模型客户端 — 能力设计参考

> **性质**：本文档不绑定任何具体框架、语言、操作系统或特定客户端。所有设计均从**第一性原理**推导——即"任何 agent 框架想把工作委托给一个以 CLI 形式提供的外部模型客户端时，都必须解决的设计问题"。
> **主语是「能力（capability）」，不是某个实现。**
> **适用对象**：任何需要把任务委托给本地 CLI 子进程（各类 coding / 对话 agent CLI 等）的 agent 平台。
> **不覆盖**：SDK / HTTP API 直连、纯云端推理、浏览器内推理。如你的平台只用这些，本文多数决策不适用。

---

## 0. 读法与范围

1. 先读 §1 建立通用问题空间，再按 §2 逐条能力选型，最后用 §3 决策框架与 §4 组合模式收敛到你的实现。
2. 每条能力给出：**问题 → 变体（设计选项）→ 权衡 → 选型原则 → 组合提示**。
3. 文档不预置"该用哪个客户端"，只预置"该具备哪些能力、各能力何时选用"。

---

## 1. 通用问题空间（任何 agent 都绕不开）

当一个 agent 框架要把任务委托给外部 CLI 模型客户端，它在**进程层面**必须解决 6 件事，另有 2 个横切关注点：

| # | 关注点 | 本质问题 |
|---|--------|----------|
| 1 | 启动（Spawn） | 以什么方式、带什么参数/环境拉起子进程 |
| 2 | 通信（Transport） | 如何把输入喂进去、把输出/流式结果取出来 |
| 3 | 连续性（Continuity） | 跨多轮对话如何保持上下文 |
| 4 | 自省（Capability） | 框架怎么知道这个客户端能/不能做什么 |
| 5 | 凭据（Credential） | 密钥/令牌怎么安全传入 |
| 6 | 回收（Lifecycle） | 任务取消、进程退出、资源泄漏怎么兜底 |
| ⊕ | 并发（Concurrency） | 同一客户端如何服务多个并发任务 |
| ⊕ | 监督（Supervision） | 子进程崩溃/卡死如何兜底恢复 |

这 8 项即 §2 能力清单的来源。它们彼此独立、可单独选型、按需组合。

## 2. 能力模型（原子单位）

### C1 — 进程启动与生命周期（Spawn & Lifecycle）

- **问题**：子进程如何被拉起与结束。
- **变体**
  - **一次性（one-shot）**：每任务 spawn，结束即退出。→ 最简单、隔离最好、无跨轮状态，但每次付启动税。
  - **长驻（long-lived）**：进程常驻，多轮复用同一进程。→ 省启动开销，但状态累积、需显式回收。
  - **守护（daemon）**：detached 后台进程，对外暴露 session / REST 接口，框架经 HTTP 交互。→ 解耦最彻底、可跨进程/跨会话持久，但引入网络面与编排复杂度。
- **权衡**：一次性隔离性/正确性最好但启动税高；长驻省税但状态与泄漏风险升高；守护最灵活但最重。
- **选型**：本地、可信、短任务 → 一次性；长对话、需同上下文 → 长驻/守护。
- **关键契约**：spawn 应返回一个**句柄（handle）**，句柄携带 `owner token`；回收时按 token 而非进程名。

### C2 — 传输与 I/O 契约（Transport）

- **问题**：框架与子进程之间如何交换消息。
- **变体（控制面）**
  - **stdout JSON-lines 流式（pull）**：子进程把结构化事件打印到 stdout，框架逐行解析。→ 最通用、易调试、确定性高。
  - **守护 REST / session 轮询**：框架主动 GET/POST，结果存服务端。→ 适合异步、可恢复，但需会话管理。
  - **文件 / socket 旁路**：超大产物走文件，控制面走管道。
- **变体（终端形态）**
  - **管道（pipe）**：非交互，确定性高、安全。→ **默认**。
  - **PTY**：模拟终端，某些客户端在需要用户确认/交互工具时必需。→ 代价：输出含转义、难解析、需 expect 逻辑。
- **原则（通用、强）**：**stderr 是旁路诊断信号，不是续命信号。** 框架不应因 stderr 有内容就判定进程存活或需要保活；存活判定应基于 stdout 心跳 / 退出码 / 句柄状态。

### C3 — 会话连续性与恢复（Session Continuity）

- **问题**：跨轮次如何保留上下文。
- **变体**
  - **无状态**：每轮全新上下文。→ 隔离、可预测，但重复付费、无记忆。
  - **可恢复（resume）**：客户端给 session id，框架凭 id 续上。→ 平衡。
  - **持久工作区**：客户端维护长期 workspace / 记忆。→ 最强连续，但上下文膨胀与隐私/成本风险上升。
- **契约（session strategy contract）**：客户端应**声明**它如何保上下文（none / id / workspace），框架据此决定能否跨进程续接。
- **权衡**：连续性强 → 成本/隐私/膨胀上升。应在任务边界显式决定"本任务是否允许复用上文"。

### C4 — 能力声明与协商（Capability Declaration）

- **问题**：框架如何知道客户端"能/不能"做什么，且不靠运行时试错。
- **分层（关键）**
  - **静态能力（type-level）**：编译期 / 类型层可选方法或能力标志，如 `SupportsMultiplexing`、`SupportsPTY`、`SupportsBackgroundDaemon`、`SupportsSessionResume`。一经实现即存在，不随调用变化。
  - **调用绑定（invocation-binding）**：同一次调用内、随配置/上下文变化的属性，如本次 token 预算、是否 interactive、绑定的上下文容量。
- **原则（通用、强）**：**静态能力不要塞进动态绑定，反之亦然。** 把"是否支持多路"做成运行时探测会导致脆弱的分支与"恰好没实现"的静默失败。
- **协商策略**：优先静态声明 + 可选运行时细化；避免"先试后知"。

### C5 — 凭据与密钥（Credential）

- **问题**：密钥/令牌如何安全传入子进程。
- **变体**
  - **环境变量**：框架 setenv 后 spawn。→ 常用、不进 argv。
  - **配置文件**：客户端自读受护文件（如 `0600`）。→ 适合持久、可轮换。
  - **云端席位（no local key）**：客户端走云端身份，本地无密钥。→ 最省心，需联网与信任云端。
  - **交互式 stdin 提示**：启动时从 stdin 读。→ 不适合自动化。
- **原则（通用、强）**：**密钥绝不进进程参数（argv 暴露在 `ps` / 进程列表）**；优先 env 或受护文件；凭据与调用解耦（可在不碰代码时轮换）。

### C6 — 并发与多路（Concurrency / Multiplexing）

- **问题**：同一客户端如何服务多个并发任务。
- **变体**
  - **每任务独立进程（parallel）**：隔离、正确，但资源占用高。→ **默认安全**。
  - **单进程多路（multiplex）**：一个长驻进程按 session 路由多任务。→ 省资源。
- **风险（通用、强）**：**把有状态客户端多路到无关任务会上下文串味（context bleed）**。多路仅当客户端保证会话隔离时才安全。
- **选型**：无状态/隔离客户端 → 可多路；有状态且共享上下文 → 必须每任务独立或严格 session 隔离。

### C7 — 取消与回收（Cancellation & Teardown）

- **问题**：任务中止、进程退出、孤儿进程怎么处理。
- **单一终止入口**：取消应走一个信号 / abort 通道（如 `AbortSignal`），而非散落各处的 kill。
- **回收按 owner**：进程与 `owner token` 绑定；owner 退出/取消时按 token 回收其派生进程。
- **反模式（通用、强）**：**`pkill -f <pattern>` 按进程名/命令行模式杀**——会误杀名字相似的无辜进程，在多 agent 主机上危险。
- **原则**：存活判定与回收都基于句柄/owner，不基于文本模式。

### C8 — 监督与恢复（Supervision）

- **问题**：子进程崩溃/卡死如何兜底。
- **变体**
  - **无**：框架不接管，崩溃即失败。→ 简单。
  - **监督者（supervisor）**：框架侧或独立进程监测、按需重启或接管句柄。→ 韧性高。
  - **孤儿检测**：定期扫描无 owner 的孤儿进程并回收。→ 防泄漏。
- **权衡**：监督提升韧性，但增加复杂度与"静默重启掩盖 bug"的风险。

### C9 — 自适应投入（Adaptive Effort）

- **问题**：是否每次调用都付"重型"成本（守护 + 多路 + 监督）？
- **原则（通用、强）**：**按任务风险/复杂度匹配调用成本**——轻任务走一次性 pipe，重任务才升档到守护/多路。避免为琐碎任务付守护开销，也避免为重任务用一次性导致状态丢失。
- **表达**：框架持有一组调用档（lightweight / full），按任务元数据选档。

### C10 — 调用绑定与资源预算（Invocation Binding / Budget）

- **问题**：如何防止被委托的工作失控（无限上下文、超时、烧钱）。
- **原则（通用、强）**：每次委托**绑定有限预算**——token 上限、时间上限、成本上限；客户端超预算应拒绝或降级，而非无限推进。
- **与 C3/C4 关系**：预算是动态绑定（C4 调用绑定层），连续性策略（C3）决定预算能否跨轮累积。

## 3. 决策框架（给定约束，该要哪些能力）

最小必需集随部署/信任模型变化：

| 部署 / 信任模型 | 必需能力（最小集） |
|----------------|--------------------|
| 本地、单用户、可信、短任务 | C1 一次性 + C2 pipe + C5 env + C7 abort |
| 本地、长对话、需记忆 | + C3 resume + C1 长驻/守护 |
| 需交互工具（客户端会 prompt） | + C2 PTY + C8 监督 |
| 多任务并发 | + C6（仅当客户端隔离）/ 或每任务独立进程 |
| 不可信 / 共享主机 | + C7 owner 回收（禁用 `pkill -f`）+ C5 受护文件 |
| 重任务 / 需韧性 | + C8 监督 + C9 自适应 + C10 预算 |

---

## 4. 参考组合模式（通用，非某实现）

- **模式 A「最小一次性」**：C1 一次性 + C2 pipe + stdout JSON + C5 env + C7 abort。→ 本地可信短任务。
- **模式 B「有状态会话」**：C1 守护 + C2 REST + C3 resume + C4 静态能力 + C5 受护文件 + C7 owner 回收。→ 长对话/持久。
- **模式 C「交互式」**：C1 长驻 + C2 PTY + C8 监督 + C7 abort。→ 会 prompt 的客户端。

---

## 5. 反模式（通用，务必避免）

1. `pkill -f` 按模式杀进程（误杀无辜）。
2. 密钥进 argv（`ps` 暴露）。
3. 把 stderr 当存活信号（误判保活）。
4. 静态能力塞进运行时探测（脆弱分支）。
5. 有状态客户端多路到无关任务（上下文串味）。
6. 委托工作无预算上限（失控烧钱/超时）。
7. 回收靠文本模式而非 owner token。
8. 一次性进程硬扛长对话（状态丢失）。

## 6. 接入一个新客户端（通用 onboarding 清单）

新增一个 CLI 客户端的本质不是"加一个 switch case"，而是"**声明一组能力**"：

1. 在客户端注册表声明 `client id`（两层 gate：允许名单 + 配置 schema 校验）。
2. 声明 **spawn 变体**（C1）、**传输变体**（C2）、是否需要 PTY。
3. 声明 **会话策略**（C3：none / id / workspace）。
4. 声明 **静态能力标志**（C4：multiplexing / pty / daemon / resume …）。
5. 声明 **凭据方式**（C5）。
6. 实现 **传输契约**（解析 stdout JSON / 对接 REST）。
7. 提供 **默认配置与 seed** 值。
8. 在 **能力矩阵** 登记，便于框架按任务选档（C9）。

→ **关键**：新增客户端 = 填一张能力声明表 + 实现传输契约；框架其余逻辑不变。这与"在代码里堆 `switch(clientId)`"有本质区别——能力是数据/类型驱动的，分支是显式且有限的。

## 7. 开放问题（通用）

- 能力协商能否在"静态声明"与"运行时自省"间找到更安全的中间态？
- 多路复用在有状态客户端上，会话隔离的保证该由谁负责（客户端还是框架）？
- 跨运行时 / 跨主机的会话透明性，边界在哪（隐私 / 成本 / 一致性）？
- 自适应投入的"选档"依据，应由任务元数据还是历史表现驱动？
