# 多 Agent 协作系统设计文档

> **文档性质**：面向"从零构建一个多 Agent 协作系统"的设计规范。
> **内容来源**：本设计的每一条约束都提炼自一个长期运行的真实多 Agent 协作生产系统，包括其架构文档、决策记录与故障复盘。文中不带任何具体项目的命名、编号或代码引用——它是可直接套用的通用设计，而非对某个系统的描述。
> **使用方式**：每章末尾列出「必须做出的决策」，并给出推荐默认值、选择依据与验收标准。你可按附录 A 的决策清单逐项拍板，按第 15 章的落地顺序分阶段实现。

---

## 0. 适用范围与前提

### 0.1 本设计针对的系统形态

- 系统中有 **N 个独立的 Agent**，每个 Agent 是一个独立的模型会话或进程（可来自不同厂商、不同模型、不同工具集）。
- Agent 的能力边界由**外部工具**决定，而不是由模型自身决定。Agent 能读写文件、执行命令、调用服务。
- 系统有**一个或多个人类所有者（Owner）**，拥有最终裁决权。
- Agent 之间需要**互相派活**：把一个任务连同上下文交给另一个 Agent，并等待它回话。
- 任务可能持续很久（跨小时、跨天），因此 **状态必须持久化**，进程可能重启。

### 0.2 明确非目标

- 不做"Agent 自主涌现协作"——协作语义必须是平台的一等能力，有明确的数据结构与状态机。
- 不做 Agent 之间的自由文本闲聊式协作——每一轮协作都应有可观测的载体（任务、消息、事件）。
- 不预设 Agent 的分工是静态的——分工应由路由与准入机制动态决定。
- 不引入向量数据库作为协作的必需条件——协作靠结构化状态，不靠语义检索。

## 1. 五条不变量（Invariants）

这五条是**跨全系统的铁律**。它们不是建议，而是所有其他设计必须服从的公理。任何一处违反，都会在多 Agent 并发下产生难以复现的故障。

| 编号 | 不变量 | 内容 | 它防住什么 |
|---|---|---|---|
| **INV-1** | 单一所有者 | 任何一个事实、任务或资源，在任意时刻只有一个所有者 Agent。 | 两个 Agent 同时认为自己负责同一任务，互相覆盖工作成果。 |
| **INV-2** | 单一切换点 | 状态的持久化迁移只有一个切点，且排序由一个唯一的比较器决定。 | 多个写入路径各自排序，产生顺序歧义与重复执行。 |
| **INV-3** | 不跨事实推断 | 身份、准入资格、可见性、已处理状态四类事实互不推断——A 成立不能推出 B 成立。 | 用"消息存在"推断"已投递"，用"已入队"推断"可执行"，导致状态错位。 |
| **INV-4** | 单一终态 | 每一个被准入的请求，最终只产生一个终态（成功 / 失败 / 取消）。 | 同一请求被两条路径各自收尾，账目对不上。 |
| **INV-5** | 投影可重建，歧义即拒绝 | 所有派生视图必须能从权威账本重建；当状态有歧义时，**拒绝执行而不是猜测**（fail-closed）。 | 猜测式的容错把一次小偏差放大成系统性错误。 |

**必须做出的决策**
- D1.1 你的系统里，"事实的唯一所有者"用什么标识？（推荐：`(任务ID)` 而非 `(Agent, 线程)`——后者会在 Agent 重启后失配）
- D1.2 fail-closed 的边界在哪？（推荐：**只拒绝无法证明安全的请求，不要扩大打击面**——见 §14 的爆炸半径教训）

## 2. 架构分层

### 2.1 三层结构

```
┌─────────────────────────────────────────────┐
│  人类层（Owner）                             │
│  目标设定 · 最终裁决 · 不可逆操作授权          │
├─────────────────────────────────────────────┤
│  平台层（协作内核）                           │
│  身份与会话 · 路由与投递 · 统一执行平面         │
│  任务所有权 · 治理门禁 · 记忆与证据            │
├─────────────────────────────────────────────┤
│  模型层（Agent 运行时）                       │
│  CLI 进程 / 会话 / 工具集 / 各厂商模型         │
└─────────────────────────────────────────────┘
```

**关键判断：协作语义属于平台层，不属于模型层。**
Agent 之间怎么交接、谁在什么条件下必须评审、消息何时可见——这些必须是平台层用代码承载的能力。把协作规则写进 Agent 的提示词、寄望于模型自觉遵守，是这套体系里最贵的一课（见 §9.6）。

### 2.2 平台层六大组件

| 组件 | 职责 | 不做什么 |
|---|---|---|
| **身份与会话管理** | 分配稳定 Agent 身份；管理会话生命周期与恢复 | 不管任务内容 |
| **路由与投递** | 解析寻址、决定目标、把工作送进执行平面 | 不做业务判断 |
| **统一执行平面** | 所有执行请求的唯一入口、排队、准入、执行、收尾 | 不区分请求来自人还是 Agent |
| **任务所有权** | 追踪"谁现在负责什么"，承载交接与等待 | 不承载任务内容本身 |
| **治理门禁** | 在关键节点施加不可绕过的检查 | 不做常规质量建议 |
| **记忆与证据** | 持久化事实、追加事件、提供可重建的投影 | 不做不可追溯的缓存 |

**必须做出的决策**
- D2.1 Agent 调用方式是"子进程 + 回传通道"还是"API 直连"？
  - **推荐默认**：**子进程 + 回传通道**。理由：能完整保留 Agent 的工具能力与订阅额度；纯 API 直连会丢失 Agent 能力（只能对话，不能动手）。
  - 若必须支持 API 直连，把它作为**只读的旁路**，不要让它是独立运行时——否则安全基线要维护两套。
- D2.2 协作语义是否独立于 Agent 运行时？**推荐：是。** Agent 换厂商不应影响协作协议。

## 3. 实体模型

| 实体 | 定义 | 关键字段 |
|---|---|---|
| **Agent** | 一个可被寻址、可被唤醒的工作单元 | 稳定 ID、能力标签、可用工具集、当前归属线程 |
| **身份（Identity）** | Agent 的自我声明，必须在**每次上下文构建时**注入 | 名称、角色、协作协议格式 |
| **会话（Session）** | Agent 与模型的一次连续对话上下文 | 会话 ID、所属线程、可恢复点 |
| **线程（Thread）** | 协作的工作单元，是排队与隔离的边界 | 线程 ID、参与者集合、当前所有者 |
| **调用（Invocation）** | 一次"Agent 被唤醒并执行"的实例 | 调用 ID、父调用 ID、状态、开始/结束时间 |
| **消息（Message）** | 一次可投递的内容单元 | 消息 ID、投递状态、来源、目标 |
| **任务承担权（Custody）** | "谁现在负责把这个任务推进下去" | 承担者、进入时间、等待条件、等待期限 |
| **事件（Event）** | 追加式的状态变更记录 | 事件类型、序号、时间戳、关联实体 |

**必须做出的决策**
- D3.1 "线程"是隔离与并发的边界吗？**推荐：是。** 不同线程的 Agent 实例互不共享状态，跨线程通信必须显式申请。
- D3.2 身份是"常量"还是"会话开始时算一次"？**推荐：常量，每次上下文构建都必须注入**——上下文压缩后丢失身份声明，会让 Agent 忘记自己是谁、忘记协作协议的格式（这是真实发生过的退化）。

## 4. 统一执行平面

**核心决策：所有执行请求走同一条通道。**

不管请求来自人、来自另一个 Agent、还是来自外部系统，都构造成同一种队列条目，进入同一个执行平面。多个执行平面会产生不可见的旁路，而旁路意味着不可观测、不可干预。

### 4.1 队列条目类型

| 类型 | 语义 | 典型来源 |
|---|---|---|
| 用户输入 | 人的直接指令 | Owner |
| 唤醒投递 | Agent 被另一个 Agent 唤起 | 路由层 |
| 私有输入 | 只对特定执行者可见的输入 | 系统内部 |

**这三类必须共用同一套排队/准入/收尾逻辑**，而不是各建一条队列。共用通道的收益：统一的顺序语义、统一的准入判断、统一的审计。

### 4.2 排序与出队

- **单一比较器**决定顺序，比较键推荐为：位置 → 优先级 → 入队时间 → ID。
- **严格队头出队**：只有队头可以被取出执行，不允许跳过。
- **每个线程独立排队**，线程之间并行。

### 4.3 触发机制：脏位事件，而不是定时器

不要在"有人可能积压了工作"这件事上装一个周期性看门狗。正确做法是：**状态发生迁移时本身就把队列标脏**，由状态迁移驱动一次排空尝试。

理由：定时器式补救会产生两种失败——检查间隔太短浪费资源、间隔太长消息静默积压。而"状态迁移驱动"让积压**在模型层面不可能存在**。

**必须做出的决策**
- D4.1 队列是每线程一条，还是全局一条？**推荐：每线程一条。** 全局队列会让一个慢任务阻塞所有人的入队。
- D4.2 排序里要不要有"优先级"？**推荐：要，但严格限制使用场景**——紧急标记只给人和系统，不给 Agent 之间的常规协作（否则所有 Agent 都标紧急，等于没有优先级）。
- D4.3 准入失败怎么处理？**推荐：fail-closed**。无法确定准入身份时，记为"未归属"并拒绝执行，**不要回退到"取该线程最近一条"**——那种回退会在并发下把消息派给错误的 Agent。

## 5. 寻址与路由

### 5.1 寻址语法

- **行首约定**：只有当寻址标记出现在内容行首时才触发派发。写在句子中间的是普通文本，不是路由指令。这条约定把"讨论某 Agent"和"派活给某 Agent"区分开。
- **无标记时的兜底**：没有指定目标时，路由到该线程中最近一次发言的 Agent，而不是丢掉或广播。
- **群体寻址**：支持 `@全体` / `@某能力组` / `@本线程所有参与者`。群体标记必须在个体标记**之前**解析，且采用最长匹配优先。

### 5.2 机械路由与语义判断的分层

这是路由设计里最重要的一条边界：

- **最终收件人的判定必须是机械可校验的**，不能交给语义分类器。分类器会产生"看起来合理但错了"的收件人，而这类错误在并发下极难归因。
- 语义判断可以用在**非终局**的环节（比如给 Agent 提示"可能是谁"，给它参考），但提示是 advisory 的——**提示永远不能静默改写路由结果**。

### 5.3 扇出控制（硬约束）

| 约束 | 推荐值 | 理由 |
|---|---|---|
| 单次多目标派发的目标数上限 | 3 | 阻止一次误操作把线程炸开 |
| 多目标派发的执行模式 | 仅并行 | 串行多目标会引入隐式顺序依赖 |
| 必须回填回调目标 | 是 | 否则结果没有归宿 |
| 同线程已有运行中编排时 | 拒绝新编排（返回冲突） | 防扩散 |

### 5.4 路由的三层防线

1. **机械约束**（代码）：目标数上限、最终槽位校验、同线程编排互斥。
2. **循环熔断**（代码，见 §8）：检测空转并切断。
3. **行为提示**（提示词）：告诉 Agent"派活前先确认对方是否已在处理"。

**必须做出的决策**
- D5.1 无标记消息的路由策略？**推荐：路由到最后发言者。** 丢弃会静默丢活，广播会制造噪声。
- D5.2 是否允许语义分类器决定收件人？**推荐：不允许。** 只允许它给出提示。
- D5.3 群体寻址的最大解析深度？**推荐：一层。** 不允许群体标记再触发群体标记。

## 6. 任务所有权与交接

多 Agent 协作的失败，绝大多数可以归到"责任归属不清"。这一章是核心。

### 6.1 承担权交接协议（三选一）

当一个 Agent 被指派任务时，它必须三选一，不能沉默：

| 选择 | 含义 | 触发场景 |
|---|---|---|
| **接受** | 我承接，我推进 | 在我职责与本轮上下文内 |
| **退回** | 我不接，交还给派发方 | 不属于我、我缺少必要的工具或信息 |
| **升级** | 交给人类或更高层裁决 | 涉及不可逆操作、目标冲突、我无法判定 |

**关键：接受/退回/升级由被指派方自主判定，不允许平台强制派单。** 强制派单会产生"错误承诺"——Agent 接下一个它做不了的任务，然后卡住整条链路。

### 6.2 交接必须携带的五个要素

任何一次责任交接，必须同时给出：

1. **做了什么**（已完成的实际动作，不是意图）
2. **为什么这么做**（决策理由）
3. **放弃了什么**（权衡与替代方案）
4. **未决问题**（谁需要接着回答什么）
5. **下一步动作**（接手方应该做什么）

外加：**责任人签名**与**环境标注**（在哪个工作区、哪个分支、什么版本上做的）。

**只写"做了什么"的交接是不可审计的**：接手方无法判断你的选择是否仍然成立，也无法知道你有没有踩过坑。

### 6.3 完成必须由现实动作产生

**纯文本声明不能改变任务状态。**

Agent 说"我已经完成了"不构成完成。状态迁移必须锚定在一个**机器可核验的现实动作**上：一次工具调用、一次提交、一次评审结论。

推荐的状态迁移路径：
```
动作发生 → 记录完成候选 → 核验候选 → 提交完成判定（已验证）
```
中间任何一环缺失，状态都不迁移。

这一条直接防住最常见的失败：Agent 承诺"下次一定"但没有任何落地机制，任务在文本层面被标记完成，实际从未发生。

### 6.4 结构化等待（有界持球）

Agent 需要等待外部条件（人等确认、另一个 Agent 回话）时，必须发出**结构化的等待声明**，而不是把整个会话阻塞住。

等待声明的三个要求：
- **带等待条件**（在等什么）
- **带截止期限**（超时怎么办）
- **不阻塞主执行流**（等待期间该 Agent 可以处理其他线程）

**有界性**：每个时间窗口内允许的等待次数有上限（推荐默认 3）。超过上限的等待请求被拒绝，迫使 Agent 要么推进要么明确放弃——防止"无限等待"变成一种拖延策略。

### 6.5 承担权的权威记录

承担权的每一次变更都写入**追加式事件日志**，日志是唯一真相源。派生的视图（谁现在持有什么）都是从日志计算出来的投影，可以随时重建。

日志中的事件类型应覆盖：进入承担、等待、恢复、交接、退回、升级、完成、失败、超时、搁置、终止。

### 6.6 失败闭环分阶段

任务失败时，不要"一次性收摊"。分三个阶段处理：
1. **标记退化**（先承认它出问题了，停止继续投入）
2. **账本移交**（把已有进展与未决问题交接出去）
3. **轨迹归档**（记录下来，供后续分析）

**必须做出的决策**
- D6.1 是否允许强制派单？**推荐：不允许。** 被指派方必须有退回权。
- D6.2 交接五要素是硬约束还是提示？**推荐：硬约束**（平台校验字段是否齐全），但内容质量交给 Agent。
- D6.3 完成的核验标准由谁定？**推荐：平台定义"可核验动作"的类型清单**（提交、测试通过、评审通过、外部确认），Agent 声明属于哪一类。
- D6.4 等待上限超时后的默认动作？**推荐：退回给派发方**，而不是静默失败。

## 7. 并发、隔离与幂等

多 Agent 并发是 bug 的主要来源。这一章给出五条具体机制。

### 7.1 锁粒度：每线程 × 每 Agent

不要用"每线程一把锁"。那会让一个 Agent 执行时阻塞同线程的其他 Agent。

**推荐粒度**：`(线程, Agent)` 二元组一把锁。同一 Agent 在同线程内串行，不同 Agent 之间并行。

### 7.2 并行分身默认不共享状态

同一个 Agent 可能在多个线程中并行工作（"并行分身"）。**这些分身默认不共享上下文与状态。**

如果确实需要共享，必须显式声明，并且共享的是**只读快照**，不是可变引用。可变共享会让两个分身的修改互相踩踏，且极难复现。

### 7.3 同回合后续输入：抢占重启

当 Agent 正在处理时，同一个"回合"内又来了新输入：

**推荐策略：取消当前执行，用新的输入重启**（后到者胜出）。而不是排队等它做完——因为排队的语义是"按旧目标继续"，而用户的新输入往往已经改变目标。

### 7.4 幂等与去重

- 每个可重放的操作带**幂等键**，键的生成与去重必须**原子**（一次原子操作完成"检查+写入"）。
- 同一条消息的重放不得产生第二次副作用。
- 幂等键的作用域要覆盖：消息投递、任务分配、外部副作用。

### 7.5 可变性与审计的对冲

三条容易被忽略但很重要的规则：

- **不原地编辑已发出的内容**。编辑产生一个新版本/新分支，保留旧版本。理由：多 Agent 各自持有游标，原地编辑会让它们的视图错位。
- **删除保留墓碑**。软删除与硬删除都保留一个最小骨架（ID 不变），这样引用不会断裂、游标不会跳变。
- **删除走可恢复通道**，不用不可逆删除命令。

**必须做出的决策**
- D7.1 并行分身是否允许共享可变状态？**推荐：不允许**，只允许只读快照。
- D7.2 编辑是原地修改还是分支？**推荐：分支。**
- D7.3 幂等键的存储位置？**推荐：与权威账本同一存储**，保证原子性。

## 8. 循环与扩散防护

多 Agent 系统会自发产生两类恶性模式，必须用代码熔断。

### 8.1 空转循环（乒乓）

**现象**：两个 Agent 互相派活，来回若干轮，纯文本往返，谁都没有调用工具、谁都没有改变任何东西。

**熔断规则**：
- 识别"连续互派且无实质工具调用"的链条。
- 达到阈值（推荐默认 4 次）时**切断**，并把控制权交回人类。
- **判定要排除"路由类工具"本身**——否则 Agent 用一次派发工具就算"有调用"，永远不触发熔断。

### 8.2 承诺漂移（forced-pass）

**现象**：Agent 做完了自己的部分（比如给出了评审结论），但没有明确交给下一个人，任务悬在那里。

**规则**：在关键结论（评审通过/驳回、方案定稿）产生之后，**强制要求一个明确的交接动作**。没有交接动作就不算这一轮结束。

### 8.3 编排扩散

**现象**：一次多目标派发又触发新的多目标派发，扇出失控。

**规则**：同线程已有运行中的多目标编排时，拒绝新的编排请求。

**必须做出的决策**
- D8.1 熔断阈值定多少？**推荐：4 轮**（太小会误切正常的多轮讨论，太大会浪费大量 token）。
- D8.2 熔断后怎么处理？**推荐：升级给人类**，附带最近几轮的摘要——不要静默丢弃。
- D8.3 是否允许多层扇出？**推荐：不允许。**

## 9. 质量门禁与跨角色评审

**这是整套设计里最需要认真拍板的决策。**

### 9.1 铁律：非作者评审

**同一个体不能评审自己产出的内容。**

这条在多 Agent 系统里有两种实现层次：
- 弱实现：写进提示词，指望 Agent 自觉。
- 强实现：平台层记录"谁产出了什么"，在评审环节校验评审者身份 ≠ 产出者身份，不符则拒绝。

**推荐：强实现。**

### 9.2 评审者配对规则

当需要人类以外的评审者时，按以下顺序选择：

1. **跨能力族优先**——能力来源不同的评审者（不同模型/不同工具集）比同族的更能发现盲区。
2. 同族中**有评审角色**的 Agent。
3. 同族**当前空闲**的 Agent。
4. 都不可用时，**升级到人类**。

注意：**身份的判定要按个体，不能按账号。** 多个 Agent 可能共用同一个上游账号，如果按账号判定，就会让"两个不同的 Agent"被误认为同一个体，自审被放过。

### 9.3 风险分层：强制力随风险走，不随动作走

不要让"每一个改动"都走全套重流程——那会让人和 Agent 都绕过流程。也不要让高风险改动走轻流程。

**做法**：定义风险维度，命中即升级强制力等级。

| 风险维度 | 判断问题 |
|---|---|
| 行为风险 | 会改变系统的对外行为吗？ |
| 数据风险 | 会改动或删除持久化数据吗？ |
| 安全风险 | 触碰认证、权限、边界吗？ |
| 契约风险 | 改变对外接口或数据契约吗？ |
| 不可逆风险 | 出错后能回退吗？ |

**元风险**：如果改动对象是**门禁机制本身**，直接进入最高等级，且强制要求跨族非作者评审——防住"为了通过检查而修改检查"。

### 9.4 门禁的两种形态：软约束 vs 硬约束

| | 软约束 | 硬约束 |
|---|---|---|
| 载体 | 提示词 / 文档约定 | 平台代码 |
| 违反时 | 记录 + 告警，不阻断 | 阻断，必须满足条件才能继续 |
| 适用 | 判断类要求（怎么写得更好） | 安全类要求（不能自审、不能绕过、不能越权） |
| 代价 | 依赖 Agent 遵守，可能被忽略 | 可能造成阻塞，需谨慎划定边界 |

**推荐的分工**：
- **硬约束**：非作者评审、不可逆操作授权、单一所有者、幂等去重、准入 fail-closed、扇出上限。
- **软约束**：协作行为的风格建议、优先级的建议、交接内容的完整度提示。

**最危险的组合是"把安全类要求做成软约束"**——文档里写得很严，代码里只观测不阻断。当 Agent 不遵守时，系统不会拒绝，只会记一条日志。这种"看起来有门禁"的状态比没有门禁更危险，因为它让人误以为已经被保护了。

### 9.5 门禁的位置：告示牌 vs 控制器

**流程阶段应该是"公告板"，不是"必须依次通过的控制器"。**

- 阶段信息对所有人可见（谁在什么阶段、卡在哪、下一步是什么）。
- 但只有**极少数关键节点**是硬门禁（推荐：进入实际动手之前的准入、以及收尾之前的验收）。
- 中间阶段允许跳跃与回退，只要风险判定允许。

理由：把每一个阶段都做成硬门禁，会迫使 Agent 形式化地"点过"每一步，门禁就退化成仪式。

### 9.6 评审循环的状态机

推荐用一个显式状态机承载评审，每个状态有明确的进入条件与出口：

```
空 → 已请求 → 卫生检查完成 → 预评审完成 → 评审已派发
   → 意见已收集 → 判定：阻塞 / 通过 → 证据已密封 → 已合入 → 已归档
```

要点：
- **卫生检查（格式、静态检查、明显缺陷）可以自动修**。
- **判定必须由具名的评审者签署**，不能由自动程序代替。
- **证据要密封**：判定所依据的证据（测试输出、评审意见）需要被固定下来，事后可查。

### 9.7 评审的收敛

- 意见的严重级要分级（阻塞 / 应修 / 可选）。
- **只有阻塞级意见必须处理**，可选级不回环。
- 把意见**只回给提出它的那一方**，避免全广播造成的噪声与重复讨论。

**必须做出的决策**
- D9.1 非作者评审是硬约束还是软约束？**推荐：硬约束。** 这是最不该妥协的一项。
- D9.2 评审者配对的最小要求？**推荐：跨能力族优先，同族可降级，人类兜底。**
- D9.3 哪些检查可以自动修？**推荐：格式与静态检查；判定绝不。**
- D9.4 门禁硬约束的清单有几项？**推荐：控制在 5 项以内**，其余做成告警。
- D9.5 fail-closed 的打击面？**推荐：只拒绝无法证明安全的请求。** 一个未知状态不应升级成"关闭全站"（这是真实发生过的过度反应）。

## 10. 消息投递生命周期

### 10.1 三态

```
已入队 → 已投递
      ↘ 已取消
```

- **已入队但未投递的消息，不进上下文、不进时间线、不进历史**。
- 这条规则防住一个隐蔽 bug：Agent A 派活给 Agent B 的消息，在 B 真正开始执行之前就泄漏进 B 的上下文，导致 B 基于"还没送达的消息"做判断。

### 10.2 投递失败的处理

**投递失败不得触发内容重算。**

如果消息已经提交（内容已确定），传输层的失败只应触发**重试投递**，不应触发"让模型重新生成一遍答案"。重算会导致同一逻辑消息产生两份不同内容，破坏幂等。

### 10.3 跨线程通信的准入

跨线程通信必须走**显式的主体条件化规则**——按"谁向谁、在什么条件下"给出允许/拒绝矩阵，而不是一律放行。

接收方需要的上下文应**结构化注入**（直接给出结构化的引用），不要靠接收方从自然语言里解析——解析会失败，而且失败得很安静。

### 10.4 只读边界

把"投递消息"和"修改对方状态"分开。投递是通知，不是干预。需要干预时必须走显式的控制通道，并且可被人类审查。

**必须做出的决策**
- D10.1 未送达消息是否可见？**推荐：不可见**（不进上下文）。
- D10.2 跨线程通信默认允许还是默认拒绝？**推荐：默认拒绝 + 白名单矩阵。**
- D10.3 传输失败的重试上限？**推荐：有界重试 + 最终告警**，不静默。

## 11. 状态、记忆与真相源

### 11.1 单一真相源

每个概念只有一个定义处，状态信息只有一个存储点。**同一信息有两个写入路径，就一定会有漂移。**

### 11.2 追加日志 + 可重建投影

- 权威记录是**追加式日志**。
- 所有查询视图都是**投影**，可以从日志重算。
- **不做物化的第二份索引**——需要"审批列表"时，从权威记录读穿计算，而不是维护一张会漂移的索引表。

### 11.3 不做"拼装式全景视图"

如果要给人类看全局进度，**从权威账本投影出来**，不要从多个来源拼接一个"看起来完整"的视图。

拼接视图会产生"第二真相"：它和权威账本不一致时，人不知道该信哪个，而它又常常比账本好看，于是误导决策。

### 11.4 用户数据不得静默消失

**任何过期策略都必须是显式开启的（opt-in），默认不过期。**

理由：默认 TTL 会在无人注意时删除用户数据，且删除时没有任何提示——用户只会在很久以后发现东西不见了。这是真实踩过的坑。

### 11.5 记忆的三层

| 层 | 内容 | 写入时机 |
|---|---|---|
| 会话内 | 当前对话上下文 | 实时 |
| 工作记忆 | 任务相关的持久记录（决策、结论、未决问题） | 关键节点显式写入 |
| 长期记忆 | 跨任务可复用的知识 | 显式提炼，不自动沉淀 |

**关键**：Agent 的记忆写入要**显式触发**，不要"每轮自动生成摘要"。自动生成的记忆会累积噪声，且难以追溯来源。

**必须做出的决策**
- D11.1 是否维护物化索引？**推荐：不维护**，读穿计算。
- D11.2 数据默认过期时间？**推荐：不过期（0）**，过期必须显式配置。
- D11.3 记忆写入是自动还是显式？**推荐：显式。**

## 12. 人在回路与授权

### 12.1 人类所有者的三件事

人类在系统里只做三件事：**设定目标、裁决分歧、授权不可逆操作。** 其余由平台与 Agent 承担。

### 12.2 必须授权的操作清单

定义一个**不可逆操作白名单**，命中即需要人类授权：

- 删除持久化数据
- 强制推送覆盖远端历史
- 合并外部贡献
- 关闭/终止一个长期任务
- 激活会改变生产状态的操作

### 12.3 授权分层

| 层级 | 谁可以做 | 例子 |
|---|---|---|
| **自动** | 平台/Agent | 格式修正、静态检查修复、重试 |
| **Agent 互相确认** | 有相应角色的 Agent | 常规评审、任务交接 |
| **必须具名签署** | 指定角色的 Agent（可追溯） | 评审判定、放行 |
| **必须人类授权** | 人类所有者 | 不可逆操作、目标变更 |

### 12.4 区分"任务授权"与"立项授权"

- Agent 可以**承接并执行一个任务**。
- 但 Agent **不能自行决定要立项做什么**——"我要做这个大功能"必须由人类批准。

这条区分防住 Agent 自行扩张范围、把"顺手做的事"变成"承诺要交付的事"。

### 12.5 干预手段

人类需要能随时介入而不必重启系统：
- **抢占**：取消当前执行，用新指令重启（保留同一个队列条目）。
- **降级**：把正在执行的 Agent 标记为只读/旁路，但不中断它（用于"你先别动手，说清楚你在干什么"）。
- **停止**：精确到单个 Agent 实例，不牵连其他人。

**必须做出的决策**
- D12.1 不可逆操作清单有哪几项？
- D12.2 "具名签署"的粒度？**推荐：到具体 Agent 个体**，不是角色。
- D12.3 干预是否需要理由？**推荐：抢占需要，降级不需要**（抢占要保留审计信息）。

## 13. 可观测性与运维

### 13.1 单一存活真相源

系统的"谁在运行"必须有**唯一**的判定来源。

反面教训：如果存在多个独立的存活判定（进程表、心跳、数据库状态），它们会各自给出不同答案，产生"脑裂"——一边认为任务在跑，一边认为已经结束。修正方式是收敛成单一判定源，并把状态变更作为事件广播。

### 13.2 事件流

关键的生命周期节点都要产生事件：启动、接管、开始执行、完成、失败、超时、被中断。事件是排障的第一手材料，且必须是**结构化的**，不是日志文本。

### 13.3 运行账本

从第一天就建立运行账本：每次执行记一条，包含输入、输出、耗时、结果、归属。**成功也要记**——只在失败时记录会导致"沉默的成功"和"沉默的失败"都不可查。

### 13.4 逃生口

提供一个"强制重置运行态"的操作，但它**只能清运行状态，不能碰数据**。运维紧急时刻需要一个人能立刻让系统回到干净状态，而不用担心误删数据。

### 13.5 可视化只做投影

所有仪表盘都是权威账本的投影。不要为了"看起来更完整"而拼接多来源。

**必须做出的决策**
- D13.1 存活判定源是哪一个？**推荐：单一权威状态记录**，其余全部派生。
- D13.2 是否记录成功路径？**推荐：是。**
- D13.3 逃生口的边界？**推荐：只清运行态。**

## 14. 失败模式目录

下面每一条都是真实系统中**确实发生过**的问题，附上根因与由此产生的设计规则。这是本设计文档里最有价值的部分——它们是"想不出来、只能踩出来"的约束。

| # | 现象 | 根因 | 由此产生的规则 |
|---|---|---|---|
| 1 | 消息积压但无人执行 | 靠周期性看门狗补救积压 | 改为状态迁移驱动的排空（§4.3） |
| 2 | 跨线程状态互相污染 | 同一 Agent 的多个会话共享可变状态 | 并行分身默认不共享（§7.2） |
| 3 | 修复一个问题，引发五处新问题 | 根因修完后"顺手"附带修了触发器 | 补丁数超过 3 就停下复检方向；根因修复后独立评估是否继续（§14.1） |
| 4 | 文件被大规模误删 | 同步目标目录写错，指向了运行中的工作区 | 同步必须带目标白名单；源端必须有"只允许公开内容"的闸门 |
| 5 | 数据库重启后归零 | 持久化文件与快照脱节，冷启动加载了空数据 | 定期演练"冷启动"，不假设"以前没事就没 bug" |
| 6 | 用户数据静默消失 | 默认过期时间从 0 改成了 30 天 | 过期必须 opt-in（§11.4） |
| 7 | 测试全绿但运行时一堆问题 | 只跑单元测试，没在真实运行时验证 | 改核心路径必须在真实运行时验证（§14.2） |
| 8 | 一个未知状态导致全站不可用 | fail-closed 打击面过大 | fail-closed 只拒无法证明安全的请求（§1、§9-D9.5） |
| 9 | 决策记录与实际实现漂移 | 实现推翻假设后无人回扫相关决策文档 | 任务收尾时增加"知识影响回扫"；决策文档要有"已漂移/已被取代"状态 |
| 10 | 全局进度视图没人看 | 视图是从多来源拼装的第二真相 | 只做权威账本的投影（§11.3） |
| 11 | 两个 Agent 互相空转消耗大量额度 | 没有空转检测 | 乒乓熔断（§8.1） |
| 12 | 一个慢任务阻塞全线程 | 锁粒度是整线程 | 锁粒度改为 `(线程, Agent)`（§7.1） |
| 13 | 消息在送达前就被对方"看见" | 入队即写入了接收方上下文 | 未投递消息不进上下文（§10.1） |
| 14 | 一条消息被处理了两次 | 去重检查与写入非原子 | 幂等键原子化（§7.4） |
| 15 | 原地编辑导致多个 Agent 视图错位 | 消息可被原地修改 | 编辑即分支（§7.5） |
| 16 | 上下文压缩后 Agent 忘了自己是谁 | 身份声明只在会话开始注入一次 | 每次上下文构建都注入身份（§3-D3.2） |
| 17 | 为了通过检查而修改了检查本身 | 门禁机制未受更高等级的约束 | 元风险升级（§9.3） |
| 18 | 审批列表与权威记录对不上 | 维护了物化的第二索引 | 读穿投影，不做物化索引（§11.2） |
| 19 | 视觉上"看起来完成了"但实际没有 | 交付物只有静态画面，没有真实行为 | 验收禁止"假所有者"，只认真实的端到端行为 |
| 20 | 锚点静默漂移导致批注错位 | 位置引用在内容变化后没有重新解析 | 位置引用必须可解析，解析失败 fail-closed（attached / moved / ambiguous / orphaned 四态） |

### 14.1 关于"过度修复"这一条

这是最反直觉、也最值得单独强调的教训：

> 修好根因之后，**不要顺手去修由这个根因诱发的一堆次生问题**。那些次生问题很可能在根因修复后自己消失。如果一次性全修，你会引入一批新 bug，然后在补丁链里越陷越深。

判定规则：**同一问题域的补丁数超过 3 个时，停下来重新评估方向**，而不是继续打补丁。

### 14.2 关于"必须真实环境验证"

> 单元测试与多轮评审全绿，**不等于**在真实运行环境里能用。

规则：改动核心调用路径后，必须在真实运行时（真实进程、真实并发、真实数据）验证一次。测试环境与真实环境的差异，正好落在最脆弱的那些地方（并发时序、资源耗尽、权限边界）。

## 15. 落地顺序与验收

### 15.1 四阶段

**阶段一 · 最小可用（MVP）**

必须先立起来的地基：
1. 身份与会话（每次注入身份）
2. 统一执行平面（三类入口同一队列、严格队头、每线程排队）
3. 寻址与派发（行首约定、无标记兜底、扇出上限）
4. 任务承担权（三选一交接、五要素、追加日志）

验收：两个 Agent 能通过平台完成一次完整的"派发—承接—完成—回话"，且全过程可在日志中重建。

**阶段二 · 加固**

5. 并发隔离（`(线程, Agent)` 锁、分身不共享、同回合并发重启）
6. 幂等去重
7. 循环熔断（乒乓、强制传球、编排互斥）
8. 消息投递三态（未送达不可见）
9. 评审门禁（非作者评审作为硬约束 + 评审者配对）

验收：故意构造一个互派循环、一次重复投递、一次同回合并发，系统都能正确收敛。

**阶段三 · 成熟**

10. 风险分层与门禁位置（告示牌 + 少数硬门禁）
11. 治理与授权（不可逆清单、授权分层、立项与任务分离）
12. 可观测（单一存活源、事件流、运行账本、逃生口）
13. 记忆三层与真相源纪律

验收：一次故意注入的高风险改动会被升级到最高等级；一次人为的"未知状态"不会导致全站不可用。

**阶段四 · 扩展**

14. 跨线程/跨工作区通信（主体条件化矩阵）
15. 多工作区交付与命名空间
16. 能力注册与动态发现

### 15.2 总体验收清单

| 检查项 | 通过标准 |
|---|---|
| 单一所有者 | 任何时刻，一个任务只有一个承担者；日志可证明 |
| 统一通道 | 所有执行请求都出现在同一个队列账本中，无旁路 |
| 顺序确定 | 给定同一组入队记录，重放得到同样的顺序 |
| 身份稳定 | 上下文压缩后 Agent 仍知道自己的身份与协议格式 |
| 完成可核验 | 每个"完成"都能追溯到一次具体动作 |
| 交接完整 | 每次交接五个要素齐全，缺则不成立 |
| 有界等待 | 等待有期限、有上限，超时自动退回 |
| 无空转 | 构造一个 5 轮互派循环，系统在第 4 轮熔断 |
| 非作者评审 | 构造一次自审，平台拒绝 |
| 未送达不可见 | 入队未投递的消息不出现在接收方上下文中 |
| 不静默过期 | 不做任何配置时，数据不消失 |
| 单一存活源 | 杀进程/重启后，系统状态判定唯一且正确 |
| 逃生口安全 | 强制重置后数据完好 |
| fail-closed 有界 | 单个未知状态不会导致整体不可用 |

## 16. 会话接续与交接注入

### 16.1 第一部为何不够

§6.2 要求交接携带五要素，但没说这五要素**怎么到达**下一个上下文。现实里最常见的失败是：交接写了，但被后到的上下文压缩静默吃掉，导致"下一棒"从一份有损摘要起步，丢失了关键意图与未决问题。§6 讲的是"交接的内容"，这里补的是"交接的**投递与注入**"。

### 16.2 设计要点

1. **两种上下文延续机制必须分开，不要混为一谈：**
   - **静默压缩（有损）**：上下文超阈值时自动摘要，无人工干预，保真度低，可能丢掉关键意图与未决问题。
   - **显式接力（高保真）**：Agent 在**干净断点**主动封印当前会话，把一份高保真交接note交给"下一个自己"（同线程、同 Agent、序号 +1）。
   - 二者**正交**：压缩是兜底，接力是优雅交接。不要把接力实现成压缩的触发器，也不要用接力去替代压缩。
2. **交接note 必须是 always-keep**：身份、工具清单、交接note 三类属于"永远保留"，**不参与预算不足时的裁剪**。理由：一旦开启抽取/压缩默认，交接note 若被裁掉，下一次醒来就退化成有损摘要——这正好抵消了接力的全部意义。
3. **陈旧交接隔离（关键细节）**：只注入"由**上一位主动接力封印**"而产生的note。阈值触发的封印，即使记录上残留了旧note，也**不得注入**——否则会把上一棒的历史note当成这一棒的交接。
4. **会话链**：每个会话有稳定序号、是否已封印、是否可检索。被封存的会话成为**可查询历史**（供后续检索证据），但不再是"当前上下文"。
5. **有界注入**：always-keep 也要**封顶**（给交接note 一个 token 预算），否则一条超长note 会把地基 section 挤出硬上限，反而没空间留给可变内容。
6. **注入即拼装顺序**：上下文 = 身份 + 交接note + 记忆 + 回忆指针 + 摘要 + 任务快照 + 工具。裁剪顺序从**最低优先级**开始（回忆 → 任务快照 → 摘要 → 记忆），地基（身份 / 交接note / 工具）不裁。

### 16.3 双向钢人论证

**钢人（支持）**
把交接做成平台层的 always-keep 注入，是"记忆不丢失"唯一**可验证**的实现。若交给 Agent 自觉把note 写进对话，压缩会静默吞掉它，且事后无从审计。always-keep + 陈旧隔离，让"下一棒从完整意图起步"成为**结构性保证**，而不是运气。对跨小时、跨天的长任务，这是可用性的地基。

**反向钢人（反对）**
这套做法的代价是**上下文地基越来越重**。always-keep 集合越大，留给"可变内容"的预算越少，可能把真正重要的实时记忆、证据挤出窗口。而且"强制封印 + 重启"引入了额外延迟与一次跨会话的语义断点，对短任务纯属负担。更激进的反对：Agent 完全可以在**同一会话内**自我摘要，平台不该插手会话生命周期，插手只会制造"平台与 Agent 争夺上下文控制权"的复杂度。

**裁决**
采用，但**限定触发面**：只在"上下文开始变重且存在自然断点"时由 **Agent 主动发起**，平台只提供通道、不强制、不自动触发接力（与 §11.5"记忆写入显式触发"一致）。always-keep 集合**保持极小**（身份 / 工具 / 交接note 三项封顶），其余一律可裁。短任务不接力。

### 16.4 必须做出的决策

- **D16.1** 上下文延续是否区分"压缩"与"接力"？**推荐：区分。** 压缩 = 兜底，接力 = 显式。
- **D16.2** 交接note 是否 always-keep？**推荐：是，但封顶。**
- **D16.3** 陈旧note 是否注入？**推荐：不注入**，按"封印原因"门控。
- **D16.4** 接力触发：平台自动 vs Agent 主动？**推荐：Agent 主动，平台只提供通道。**
- **D16.5** 封印后的旧会话是否可检索？**推荐：可检索**（作为证据历史），但不进当前上下文。

## 17. 提交点与崩溃恢复

### 17.1 第一部为何不够

§6.5 只说"追加日志是真相源"，§7.4 只说"幂等键要原子"。但一个**跨多个存储**写入的操作，在**写到一半进程崩溃**时怎么办？第一部没有给出协议。这一章补的就是"半完成状态"的处理。

### 17.2 设计要点

1. **提交点模型**：把一次不可逆变更拆成三段——**预提交步骤 → 提交点（不可逆） → 收尾**。
   - 例（封印会话并续接）：① 先持久化交接note（预提交，可重来）→ ② 置会话为"封印中"并清活动指针（**提交点，不可逆**）→ ③ 入队续接 + 标记提案已批准（收尾）。
2. **两处独立写入 + checkpoint 字段**：为了在崩溃后判断"到底过没过提交点"，在权威记录上记录**每个阶段的 checkpoint**（如 note 已持久化的时间、已封印的会话ID、续接条目ID）。
3. **只向前恢复，绝不回滚**：崩溃恢复时**跨查提交点是否已过**。已过 → **recover-forward**（补齐收尾）；未过 → 让提案过期、原会话继续。**永不回滚一个已过提交点的操作**，否则会留下"封印了但没续接"的**孤儿**，比原问题更难收拾。
4. **CAS 状态转移防并发双批**：两个并发的"批准"必须只有一个成功。用一次**原子比较并交换**（CAS）把状态从"待批/批准中"抢成"批准中"，失败方直接退出。
5. **原子化"状态转移 + 索引更新"**：状态变更与它的派生索引更新必须在**同一个原子操作**内完成，否则会留下"状态已终态、但索引没更新"的崩溃窗口，使该记录对基于索引的查询**永久不可见**。
6. **传输重试去重与持久状态分离**：传输层重试用一个**有界 TTL** 的去重键（临时、自动清理）；持久状态**永不过期**（§11.4）。两者混用，要么丢状态，要么垃圾键永留。

### 17.3 双向钢人论证

**钢人（支持）**
只要系统跨小时/跨天且会重启，崩溃窗口就是**必然**。提交点 + 只向前恢复，把"半完成"从"需要人工比对、可能留孤儿"降级为"自动补齐"，是可用性的硬保障。而"状态转移 + 索引更新"原子化，用一条脚本消除窗口，成本极低、收益确定。

**反向钢人（反对）**
这是一套**很重**的协议。分布式事务的复杂度是出了名的；多数场景里"崩溃恰好落在两次写入之间"概率极低——为一个极小概率窗口引入提交点、checkpoint 字段、recover-forward 分支，会让代码路径翻倍、测试面爆炸。更糟的是：recover-forward 自己写错，会制造**比原来更难查**的幽灵状态。更务实的替代是：**把整个变更塞进单一存储的单次原子写**，从根上就不需要跨写恢复。

**裁决**
**分情况，且优先消灭问题本身**：① 首选把变更**收敛成"单存储单次原子写"**，这样根本不需要提交点；② 只有当变更**本质上跨存储/跨系统**（例如先写文件系统、再写队列，或跨两个服务）时，才上"提交点 + 只向前恢复"，并把终态唯一性交给 CAS 与原子"转移+索引"。**绝不为了统一，而把本可原子化的写入硬拆成预提交 + 提交点。**

### 17.4 必须做出的决策

- **D17.1** 变更能否收敛为单次原子写？**推荐：优先收敛**（能不跨写就不跨写）。
- **D17.2** 跨存储变更是否用提交点 + 只向前恢复？**推荐：是。**
- **D17.3** 恢复时是否允许回滚已过提交点的操作？**推荐：绝不。**
- **D17.4** 并发批准如何互斥？**推荐：CAS 抢锁，失败方退出。**
- **D17.5** 去重键的 TTL 与持久状态的关系？**推荐：去重键有界 TTL，与持久状态**分离**存储。**

## 18. 派发契约：显式串行 / 并行

### 18.1 第一部为何不够

§5.2 说"最终收件人必须机械可校验"，§5.3 给了扇出上限，但没说**执行模式（串行还是并行）怎么决定**。这是最容易出事的地方：一旦让模型从上下文里推断"该串行还是并行"，就一定会错。

### 18.2 设计要点

1. **执行模式是一等字段**：`mode: serial | parallel` 必须**显式给出**，**不从目标数量推断、不从正文措辞推断、不从语气推断**。
2. **串行（serial）**：目标按工作清单**逐个**唤醒，每个看到前一个的结果，并可能**追加新目标**（链式 @）。串行的语义是"一个接一个，后者见前者"。
3. **并行（parallel）**：同一批目标**同时**唤醒、互不可见，用于"刻意的独立评审 / 发散"，**必须额外给出"并行意图"**（说明为什么它们应当彼此独立）。并行**从不链式**（防止扇出失控）。
4. **默认串行**：多目标但未声明并行意图 → **串行**派发，并对调用方回一条"已串行化"的提示。
5. **诚实显示**：给人类的进度视图必须区分"串行已启动 / 串行排队中 / 并行"，**只画真实发生的调度**，不做美化。
6. **重复目标去重**：同一目标在一次派发里只出现一次。

### 18.3 双向钢人论证

**钢人（支持）**
把串行/并行做成显式字段，直接消灭了"正文里写'你们并行讨论一下'就被误判成并行"这类事故。机械、可测试、可审计；**默认串行**还顺带抑制了扇出爆炸。对"评审"这种需要"后者见前者"的场景，串行语义正是想要的。

**反向钢人（反对）**
这剥夺了系统的"理解力"。人类说"你俩同时看看"语义其实很明确，硬要调用方改写成结构化字段，增加了 API 复杂度与认知负担；而且当调用方（尤其是模型）忘记填意图时，系统宁可"串行化"也不领会，把灵活的自然协作压成了刻板契约。更根本地：真实协作常常是**混合**的（先并行发散、再串行收敛），二值 `mode` 表达不了。

**裁决**
采用**显式契约**，但把它做成两层：**结构化字段是权威**（决定调度），**语义判断只能产出 advisory 提示**（"看起来像并行，是否切换？"），且提示**永不静默改写调度**（与 §5.2 一致）。对混合模式，用**阶段**而非单个 mode 表达（先 parallel 发散 → 人把结论交给 serial 收敛）。默认串行是对的，因为它是 **fail-safe 方向**：串行顶多变慢，并行会炸。

### 18.4 必须做出的决策

- **D18.1** 执行模式由谁决定？**推荐：结构化字段，模型不可推断。**
- **D18.2** 未声明意图的多目标派发？**推荐：串行 + 提示。**
- **D18.3** 并行是否允许链式？**推荐：不允许。**
- **D18.4** 进度显示是否允许美化？**推荐：只画真实调度。**
- **D18.5** 混合模式如何表达？**推荐：用阶段组合，而非单个 mode。**

## 19. 同体接力 vs 跨体委派

### 19.1 第一部为何不够

第一部把"交接"当**一个**概念讲。但"把活交给下一个**自己**"和"交给**另一个** Agent"，在机制上完全不同：前者的风险面是**上下文丢失**，后者的风险面是**权威错位与越权**。混在一条通道里，就会用错风险控制。

### 19.2 设计要点

1. **两种交接，两条通道：**
   - **同体接力**：封印当前会话 + 交接note 给"下一个自己"（同线程、同 Agent、序号 +1）。目标唯一、可预测，风险是上下文丢失。
   - **跨体委派**：把任务交给**另一个** Agent。涉及寻址、接受/退回（§6.1）、跨线程准入（§10.3）。
2. **同线程后继 vs 跨线程派发**：同线程单后继是延续当前讨论（目标在同一线程内）；跨线程派发需要**显式的跨线程准入**（默认拒绝 + 白名单矩阵）。
3. **"做事"与"通知"必须分开（本章最重要的一条）：**
   - **通知类**（供参考 / 协调 / 调查）→ **机械投递**，不需要人类批准。
   - **派活类**（要求对方承担工作）→ **必须经人类批准**后才投递；未批准时内容被**扣留**，只生成一个"待批提案"。
   - 理由：让一个 Agent 单方面命令另一个 Agent 承担工作是**高风险动作**（可能触发连锁、越权、额度消耗），必须有人类门禁。
4. **权威链（服务 §1 单一所有者）**：跨体委派要带上"为什么我有权派这活"的证明（显式委派 / 已接受的邀约 / 授权来源），并绑定**授权方 / 来源 / 匹配范围**。
5. **一次委派一个承担者**：同一时刻只允许一个 Agent 对该任务持有承担权（INV-1）。

### 19.3 双向钢人论证

**钢人（支持）**
区分"做事 / 通知"是这套设计里**性价比最高**的一条。绝大多数 Agent 间消息只是"同步信息"，不该走人类审批；而真正"命令对方干活"的少数消息，恰恰最该被拦。把审批只加在这 5% 上，既保住自动化，又拦住高风险，还给人类对"Agent 互相派活"的可见性。

**反向钢人（反对）**
由平台判定一条消息是"通知"还是"派活"，本身就是**语义分类**——正是 §5.2 禁止的。要么让 Agent 显式声明类别（但它可能为了绕过审批全部填"通知"），要么平台去猜（会错）。而且加人类审批会**打断 Agent 自主性**：A 让 B 帮个忙本是协作常态，现在每条都要人点批，人成了瓶颈，Agent 团队退化成"人肉调度"；审批延迟还可能让任务悬置。

**裁决**
采用"分类 + 门禁"，但有两个前提：① 分类由 **Agent 显式声明、平台可校验**（类别是结构化字段，与消息体一起提交），**绝不靠语义猜**；② 门禁**只覆盖"造成不可逆或高成本副作用"的子集**（派活、改外部状态），"给同事发个信息"默认放行。同时给审批加**批量与超时降级**，避免人成瓶颈（超时可降级为"仅通知"）。若 Agent 谎报类别，用**审计与配额**兜底，而不是试图用语义去猜。

### 19.4 必须做出的决策

- **D19.1** 同体接力与跨体委派是否共用通道？**推荐：不共用**（风险面不同）。
- **D19.2** 派活类消息是否需要人类批准？**推荐：需要；通知类默认放行。**
- **D19.3** 类别由谁定？**推荐：Agent 显式声明 + 平台校验字段。**
- **D19.4** 审批如何避免让人成瓶颈？**推荐：支持批量 + 超时降级为仅通知。**

## 20. 幂等保留与去重

### 20.1 第一部为何不够

§7.4 要求"幂等键原子"，但没定义**重试窗口内谁赢、怎么清理、释放会不会误伤**。这几个细节决定系统能不能长期跑而不累积重复执行或垃圾。

### 20.2 设计要点

1. **保留（reserve）语义**：一次性**原子 SET NX（带 TTL）**抢占去重键；成功返回**自己写入的值**，失败返回**已存在的赢家值**（调用方据此复用赢家的结果，而不是报错）。
2. **两种键的寿命不同**：
   - 传输重试去重键：**有界 TTL**（必须覆盖最大重试窗口），会自动清理、不泄漏。
   - 用户可见的状态记录：**永不过期**（§11.4）。混用会导致"要么状态被清、要么垃圾永留"。
3. **释放用"比较并删除"**：只有当键**仍指向自己的值**时才删，**绝不无条件删**——否则会把别人已顶替的保留误删。
4. **作用域覆盖三类**：消息投递、任务分配、外部副作用；且幂等键**与权威账本同存储**（保证"检查 + 写入"原子，与 §7-D7.3 一致）。

### 20.3 双向钢人论证

**钢人（支持）**
网络重试是常态，去重必须原子，否则必然重复执行（§14-14）。"失败返回赢家值"让重试天然收敛到同一结果，避免"重试报错 → 调用方以为没成功 → 再试"的放大。compare-and-delete 释放是防误删的细节——但正是这类细节决定系统能不能长期稳定。

**反向钢人（反对）**
带 TTL 的去重键有个**隐坑**：TTL 到期后**同键重试会重新执行**。如果调用方的重试窗口 > TTL，去重就形同虚设。而"失败返回赢家值"要求**所有**调用方都正确处理这个契约，任何一处漏处理就退化成静默错误。更简单的替代是：把幂等做成**账本里的唯一约束**（同一幂等键只允许一条记录），从存储层一次解决，不需要 TTL 键这套"记得清理、记得比较删除"的负担。

**裁决**
采用，但**两处收紧**：① **优先用"账本唯一约束"实现幂等**，去重键只用于**传输层**，且 TTL 必须 > 最大重试窗口，并**在文档里明写这条不等式**；② "失败返回赢家值"必须在**统一的调用封装**里做掉，不指望每个调用点各自写对。这样既保住正确性，又把"契约正确性"收敛到一个地方。

### 20.4 必须做出的决策

- **D20.1** 幂等的首选实现？**推荐：账本唯一约束。**
- **D20.2** 去重键 TTL 与重试窗口的关系？**推荐：TTL > 最大重试窗口，并写死这条不等式。**
- **D20.3** 释放语义？**推荐：比较并删除（仅当仍指向自己）。**
- **D20.4** 幂等键存储位置？**推荐：与权威账本同存储。**

## 21. 评审的独立性强制

### 21.1 第一部为何不够

§9.1 要求"非作者评审"，但只说了"评审者 ≠ 产出者"。现实中一个评审面板里可能有作者本人、可能有两个角色其实是同一个模型、也可能两个 Agent 共用同一个上游账号——"不等于作者"六个字远远不够。

### 21.2 设计要点

1. **多角色面板 + 硬性互异**：评审面板至少三个角色（**提出者 / 复评者 / 裁决者**），且**裁决者 ≠ 复评者 ≠ 作者**三者互不相等。这比"不等于作者"强一档，防住"复评者就是裁决者"的自我循环。
2. **跨能力族优先**：不同模型 / 不同工具集的评审者优先于同族；同族降级；无候选则**人类兜底**（§9.2）。
3. **按个体判定，不按账号**：多个 Agent 可能共用同一上游账号。身份必须按 **Agent 个体**，否则"两个不同 Agent"会被当同一个体，自审被放过。
4. **评审 delta 可计算**：记录"评审者给出的判定"与"作者自称的结论"之间的差异（有则记差异项，无则记零差异），作为**独立性观测指标**，避免评审退化成橡皮图章。
5. **fail-closed**：发现"自审 / 主体错配 / 载体错配"时，**拒绝承认该评审**（不是警告、不是记录后放行）。
6. **评审追踪按个体**：每次评审按 Agent 个体建立"评审周期"，而非按线程或账号。

### 21.3 双向钢人论证

**钢人（支持）**
多 Agent 系统里最贵的失败是"看起来评审了，其实没审"。要求多角色互异 + 按个体 + delta 可算，把"独立评审"从口号变成**可校验事实**，直接防住橡皮图章；fail-closed 让"应付式评审"根本无法通过。

**反向钢人（反对）**
多角色 + 跨族 + 按个体 + delta 是一套**很贵**的机制。它要求系统精确知道"谁是谁"（个体身份、能力族、账号映射），这些元数据维护成本高、易过时；要求三只不同、够格、空闲的 Agent 同时在场，在 Agent 数量少时经常**凑不齐**，于是要么等人（延迟）、要么降级（形同虚设）。"delta"更危险：它假设评审者**应当**与作者分歧，可能**惩罚正确的共识**——一个真正正确的结论本就不该有 delta，逼出 delta 反而鼓励评审者为了"显得独立"而抬杠。

**裁决**
采用**结构性最小集**，放弃过度指标：① "非作者"是**硬约束**（必须）；② "裁决者 ≠ 复评者"是**硬约束**（防自循环）；③ "跨族优先、同族降级、人类兜底"是**软性降级链**（不强制跨族）；④ delta **只做观测、不参与准入**（防变相鼓励抬杠）。Agent 池小时，允许"同一评审者 + 人类复核"作为**合法降级**，而不是阻断流程。

### 21.4 必须做出的决策

- **D21.1** 评审面板角色数？**推荐：≥ 3 且互异。**
- **D21.2** 跨族是硬性还是优先？**推荐：优先（软），人类兜底。**
- **D21.3** 身份粒度？**推荐：按 Agent 个体，不按账号。**
- **D21.4** delta 是否参与准入？**推荐：只观测，不参与。**
- **D21.5** Agent 池不足时？**推荐：允许"同一评审者 + 人类复核"降级，不阻断。**

## 附录 B：协作行为规范

平台的机制保证"不会出错"，但协作的**质量**取决于 Agent 的行为纪律。以下规范应作为行为要求注入每个 Agent（属于软约束，靠提示词承载）。

**B1. 交接即完整。** 每一次把任务交给别人，都要给全五个要素。不完整的交接等于把不确定性转嫁给下一个人。

**B2. 承诺必须落地。** 不要承诺"下一步我会做"，除非同时给出可核验的动作。做不到就明说做不到。

**B3. 三选一，不沉默。** 被指派任务时，接受、退回或升级，必须明确表态。沉默会让派发方一直等。

**B4. 等待要结构化。** 需要等外部条件时，说明等什么、等到什么时候。不要把会话挂起。

**B5. 动手前先说清楚。** 高风险动作前先给出意图与依据，让人类有机会拦截。

**B6. 不越权。** 只做被授权的范围内的事。不因为"顺手"就扩大范围。

**B7. 表达允许沉默，请求不能假装被接住，承诺不允许失踪。**
- 允许沉默：不确定时可以选择不说，不要编造。
- 请求不能被假装接住：收到请求必须真实处理或真实拒绝，不能含糊答应。
- 承诺不能失踪：一旦承诺了，必须有人追踪它的结局。

**B8. 完成靠动作，不靠声明。** "我以为完成了"不是完成。

**B9. 不做形式主义的流程点。** 门禁是为了防风险，不是为了走流程。跳过不影响风险判定的环节是被允许的。

| 承担权（Custody） | "谁现在负责把任务推进下去" |

| 门禁（Gate） | 关键节点上不可绕过的检查 |
| 投影（Projection） | 从权威账本计算出的派生视图 |
| 帐本（Ledger） | 追加式的权威状态记录 |
| fail-closed | 状态有歧义时拒绝执行，而不是猜测 |
| advisory | 仅提示、不强制改写结果的信息 |
| 静默压缩（Compression） | 上下文超阈值时自动摘要，有损、无人工干预的兜底延续 |
| 显式接力（Explicit Relay） | Agent 在干净断点主动封印会话，把高保真交接note 交给"下一个自己" |
| always-keep | 预算不足时也不裁剪的地基内容（身份 / 工具 / 交接note） |
| 陈旧note 隔离 | 只注入由"主动接力封印"产生的交接note，阈值封印残留的旧note 不注入 |
| 会话链（Session Chain） | 同一 Agent 在同一线程内的会话序列（含已封印的可检索历史） |
| 提交点（Commit Point） | 一次不可逆变更中"越过即不可回滚"的那一步 |
| 预提交（Pre-commit） | 提交点之前可安全重来的准备步骤 |
| checkpoint | 记录各阶段已完成的标记，用于崩溃后判断是否已越过提交点 |
| 只向前恢复（Recover-forward） | 崩溃后只补齐收尾，绝不回滚已过提交点的操作 |
| 孤儿（Orphan） | 已封印却没有续接的半完成状态 |
| CAS（比较并交换） | 原子地"检查状态并更新"，用于并发互斥（如抢批准） |
| 串行（serial） | 目标逐个唤醒，后者见前者，可链式追加新目标 |
| 并行（parallel） | 同批目标同时唤醒、互不可见，从不链式 |
| 执行模式（mode） | 派发的一等字段，显式声明 serial/parallel，不可从上下文推断 |
| 并行意图（parallelIntent） | 声明"为什么这些目标应当彼此独立"的结构化字段 |
| 同体接力（Self-Relay） | 把任务交给"下一个自己"（同线程、同 Agent、序号 +1） |
| 跨体委派（Delegation） | 把任务交给另一个 Agent（涉及寻址与跨线程准入） |
| 派活类 / 通知类 | 要求对方承担工作（需人类批准） vs 仅同步信息（机械投递） |
| 权威链（Authority Chain） | 证明"为何我有权派这活"的凭据链（授权方 / 来源 / 匹配范围） |
| 保留（Reserve） | 用原子 SET NX 抢占去重键的动作 |
| 去重键（Dedup Key） | 传输层重试去重用的**有界 TTL** 键（与永久状态分离） |
| 比较并删除（Compare-and-delete） | 仅当键仍指向自己的值时才删除，防止误伤他人的保留 |
| 评审面板（Review Panel） | 提出者 / 复评者 / 裁决者的多角色集合，三者硬性互异 |
| 评审 delta | 评审者判定与作者自称结论之间的差异，**仅作观测**、不参与准入 |
| 个体身份（Per-agent Identity） | 按 Agent 个体而非上游账号判定身份（防"共用账号被当同一个体"） |
